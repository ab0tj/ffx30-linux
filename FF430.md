## MultiTech FaxFinder FF430 --- Linux bring-up notes

### Hardware / platform

-   Board identifies as **MultiTech FaxFinder FFx30/FF430**.

-   SoC is an **Intel IXP42x/IXP425-family XScale** system.

-   RAM: **256 MiB** (*0x10000000*).

-   Bootloader is **RedBoot**.

-   NOR flash is on the IXP4xx expansion bus and RedBoot FIS is usable.

-   CompactFlash/IDE is on expansion-bus chip selects and works as the
    root filesystem.

-   Primary Ethernet is the IXP4xx NPE Ethernet controller and works
    under the modern kernel.

-   There are two SoC XScale UARTs:

    -   *0xc8000000*
    -   *0xc8001000*

-   Console is the first XScale UART. With the Exar driver loaded after
    boot, it remains *ttyS0*.

-   There is a **DS1302 RTC** connected to GPIO2 (SCLK), GPIO4
    (bidirectional I/O), and GPIO5 (active-high CE).

-   An apparent DT I²C EEPROM at *0x50* appears not to exist on this
    board. The only obvious EEPROM observed physically is associated
    with the Exar/modem circuitry. The attempted *at24* device therefore
    never successfully bound.

### Ethernet MAC address

The MAC isn\'t coming from an EEPROM. RedBoot stores it in its
configuration flash.

The RedBoot config partition contains:

*npe_eth0_esa*

*npe_eth1_esa*

For this particular unit, *npe_eth0_esa* contains:

*00:08:00:72:59:9f*

which matches the MAC observed externally while TFTP booting.

Relevant bytes from the RedBoot config:

*00000410 00 06 0d 01 00 6e 70 65 5f 65 74 68 30 5f 65 73*

*00000420 61 00 00 08 00 72 59 9f \...*

So eventually the MAC should probably be obtained from the RedBoot
configuration rather than hard-coded.

## Exar quad UART / modem interface

The board contains an Exar **XR17D15x-family quad PCI UART** used to
communicate with four internal modems.

Linux currently identifies the four channels as:

*uart:XR17D15X mmio:0x48000000*

*uart:XR17D15X mmio:0x48000200*

*uart:XR17D15X mmio:0x48000400*

*uart:XR17D15X mmio:0x48000600*

Thus:

-   BAR begins at *0x48000000*.
-   Four UARTs exist.
-   Channel spacing is **0x200 bytes**.
-   All four share the same interrupt.
-   There is a **14.7456 MHz crystal** physically adjacent to the Exar
    chip.
-   The resulting normal UART clock/base baud configuration appears
    correct; **TX works reliably**.

Loading *8250_exar* as a module is currently convenient because it lets
userspace configure the suspected GPIO IRQ line before probing the PCI
device and avoids having the Exar ports steal the low *ttyS* numbers
from the SoC console.

### IRQ

Extensive testing of IXP4xx GPIOs 0--12 was performed.

**GPIO 7 is the only convincing Exar interrupt candidate.**

With GPIO7 configured appropriately, Linux reports something similar to:

*24: \... IXP4GPIO 7 Level exar_uart, ttyS2*

and TX activity causes its interrupt counter to increase.

Other GPIO choices either:

-   produce no useful interrupts,
-   cause writes to stall badly, or
-   lock the machine / apparently prevent console output.

Tested interrupt polarities/types included level and edge
configurations. **Level-low is the useful configuration.** Level-high
locks the machine; falling-edge did not improve behavior.

## Important modem behavior

The four UARTs connect to actual MultiTech modems. At least the tested
modem identifies as something in the MT5634 family; old shell history
from ModemFinder contains:

*2 1.0 MT5634S*

*LT V.91.MT5634M-V92*

*NO CARRIER*

There are hardware LEDs that independently make UART/modem traffic
observable.

### TX definitely works

With an appropriate tty configuration:

*printf \'AT\\r\' \> /dev/ttyS2*

causes the TX indication, and the modem\'s RX/reply indication shows
that it recognized the command and transmitted a response.

More elaborate commands work too. It has been possible to make the modem
**dial a BBS and connect**, purely through transmitted commands.

Therefore:

**PCI access, UART addressing, baud rate, and UART TX are fundamentally
working.**

### RX fundamentally works too --- but interrupt servicing appears broken

Ordinary isolated RX generally fails.

For example:

*before:*

*tx:102761 rx:14393*

*printf \'AT\\r\'*

*after:*

*tx:102764 rx:14393*

The LEDs show that the modem received *AT* and transmitted its response,
but Linux\'s *rx* count doesn\'t increase.

However, continuously sending:

*AT\\r*

*AT\\r*

*AT\\r*

*\...*

eventually produces **large amounts of coherent ***OK*** responses**.

This is extremely important: the UART can physically receive correct
characters at the configured baud rate.

Earlier testing also occasionally produced small amounts of RX, e.g.:

*tx:37 rx:6 fe:3*

and occasional recognizable characters.

So this is **not believed to be an RX wiring or baud-rate problem**.

## FIFO observations

The normal XR17D15X FIFO configuration allows the continuous-*AT* test
to recover coherent RX.

Completely disabling the FIFO breaks operation more severely: only one
traffic LED flashes and the modem apparently no longer responds
normally.

Changing the receive trigger to:

*UART_FCR_R_TRIG_01*

has a major effect:

-   Continuous *AT\\r* is **still necessary** to make RX useful.
-   Much more received data appears.
-   Most, but not all, received characters become **doubled**.

This is a strong clue that the remaining problem is related to **RX
interrupt/FIFO servicing**, rather than the serial data rate itself.

## Stock MultiTech driver

The original OS uses a proprietary/old driver called approximately:

*mtsi_upci*

A Ghidra decompilation is available and should be kept in the repository
as reference material.

The stock driver does considerably more than simply register four
generic 16550 ports.

### PCI/UART setup

Its PCI probe ultimately calls *start_pci_pnp_board()*, which registers
the individual UARTs.

The vendor driver uses MMIO and explicitly supports the Exar device.

Its *serial_in()* / *serial_out()* functions are largely conventional
MMIO register accesses, although they contain IXP425-specific PCI access
handling when addresses aren\'t directly mapped.

### Modem reset latch

The stock driver maps:

*0x53000000*

as a modem reset latch:

*resetlatch_cs3 = \_\_ioremap(0x53000000, 0x200, 0);*

*\*resetlatch_cs3 = 0xff;*

It maintains a bitmap and can independently reset modem channels.

For the four-modem hardware variant, the reset bits are:

*modem 0 -\> bit 0*

*modem 1 -\> bit 2*

*modem 2 -\> bit 4*

*modem 3 -\> bit 6*

The same driver also contains mappings for an apparent eight-modem
variant.

This functionality has **not yet been ported** to the modern kernel.

### Stock UART initialization

*startup()* explicitly initializes Exar-specific functionality and then
calls *change_speed()*.

*change_speed()* programs:

-   IER
-   EFR/enhanced mode
-   divisor
-   LCR
-   FIFO/FCR
-   modem/flow-control behavior

Nothing discovered there yet obviously explains the RX failure, but it
provides a useful reference against generic 8250 initialization.

## Very important stock interrupt behavior

This is currently the most interesting difference.

The MultiTech driver **does not simply rely on generic 8250 shared-IRQ
polling.**

Its interrupt handler reads a device-wide Exar interrupt register at:

*BAR + 0x80*

as a **32-bit value**.

It then extracts a three-bit interrupt state for each UART approximately
as:

*status = readl(bar + 0x80);*

*status \>\>= 8;*

*cause = (status \>\> (port_number \* 3)) & 7;*

The ISR interprets the causes approximately as:

*if (cause == 1 \|\| cause == 2)*

* receive_chars(port, \...);*

*check_modem_status(port);*

*if (cause == 3)*

* transmit_chars(port, \...);*

It repeatedly rereads the global interrupt register and loops until
pending work has been serviced.

The fact that **two separate interrupt causes invoke
***receive_chars()*** is especially interesting** given the observed
FIFO/low-traffic RX behavior. One likely distinction is normal FIFO
receive versus receive timeout, but that should be verified against the
exact Exar datasheet rather than assumed.

The stock driver therefore appears to use the XR17D15x **global
interrupt-dispatch facility explicitly**, whereas modern *8250_exar*
primarily registers the UARTs with the generic 8250 infrastructure.

This is currently the strongest area for a stock-vs-upstream comparison.

## Modern *8250_exar* experiments

### MPIO configuration

Modern *8250_exar* already has *setup_gpio()* support which configures
Exar MPIO registers.

Changing these settings did **not** fix RX.

### Exar sleep/power management

A Linux kernel bug concerning XR17D15x sleep handling looked promising.

The modern driver contains:

*static void exar_pm(struct uart_port \*port,*

* unsigned int state,*

* unsigned int old)*

*{*

* serial_port_out(port, UART_EXAR_SLEEP,*

* state ? 0xff : 0);*

*}*

The driver was modified experimentally to keep the UART permanently
awake.

**No improvement.**

Sleep/power management therefore does not currently appear to explain
the FF430 behavior.

### *exar_misc_handler()*

Debugging was added to:

*exar_misc_handler()*

During the relevant experiments, **the handler was never observed to
execute at all**.

Therefore this handler does not appear to be the normal RX/TX interrupt
path on this configuration.

## Things probably ruled out

At this point these are comparatively unlikely:

-   Wrong baud rate / divisor.
-   Wrong 14.7456 MHz reference clock.
-   UART TX problem.
-   Physical RX completely disconnected.
-   Basic PCI MMIO addressing.
-   Wrong number of UARTs.
-   Ordinary termios configuration.
-   *CLOCAL*/flow-control as the underlying RX problem.
-   Exar sleep mode.
-   Exar MPIO direction/setup alone.
-   Most alternative GPIO IRQ lines.
-   Simple IRQ polarity mistake.

*CLOCAL* **is necessary for convenient command-mode testing**, because
without it tty opens can wait indefinitely for DCD.

## Root cause and working fix

The failure was reproduced with temporary instrumentation and is no
longer only a hypothesis.  Two incompatibilities with the generic 8250
path were observed.

First, when a modem reply was waiting in the FIFO, the XR17D154 global
interrupt register reported channel cause 2 (RX timeout), while the
individual channel IIR returned `0xc1` (FIFO enabled, no interrupt
pending).  At the same time LSR had data-ready set and RXCNT was nonzero.
The generic handler consequently returned unhandled and did not drain
the FIFO.  Dispatching RX-ready and RX-timeout from the global register
at BAR + `0x80`, like the stock driver, fixes this part of the problem.

Second, forcing generic byte-wide RHR draining made replies appear, but
characters were missing and fragments were delivered out of order.  The
stock driver instead uses the XR17D154 special receive FIFO-with-status
window at channel offset `0x180`.  Switching the modern driver to the
same 32-bit reads, preceded by the datasheet-required DVID dummy read,
produces complete and correctly ordered replies.

A third global cause was exposed by the second modem when CRTSCTS was
enabled.  Global cause 4 (modem/flow-control status) could likewise be
present while the individual IIR reported no interrupt.  On the
level-low shared IRQ this left the source asserted and appeared to lock
the system.  Explicitly reading MSR for cause 4, as the stock driver
does, clears it.

The final handler also retains an IIR read for global causes 3 and 4.
That read is needed to acknowledge TX-ready and cause-4 subtypes, but it
does not call the generic 8250 handler: that handler checks LSR and can
fall back to unreliable byte-wide RHR draining even when the reported
interrupt cause is TX.  TX and modem-status work are instead serviced
directly after acknowledging IIR.

The resulting service path is:

*XR17D15x global interrupt register*

* ↓*

*RX causes 1/2: 32-bit FIFO-with-status reads at channel + 0x180*

* ↓*

*modem/flow-control cause 4: read MSR*

* ↓*

*normal tty flip-buffer delivery*

All four modem channels have subsequently returned complete `ATI`
responses at 115200 baud with raw mode, CLOCAL, and CRTSCTS enabled.
The GPIO7 level-low interrupt count advances normally without an
interrupt storm.  Concurrent operation was tested with a continuous
AT-command loop on ttyS2 while ttyS3, ttyS4, and ttyS5 were used for
interactive BBS connections; no dropped or reordered characters were
observed.

### Modem reset initialization

The reset latch is on expansion-bus CS3 at `0x53000000`.  The stock
driver first configured CS3 as `0xbfff0003` and then wrote `0xff` to the
latch to release all four active-low modem reset inputs.  Without this,
some modems fail to assert CTS/DSR; CRTSCTS then correctly blocks TX and
programs such as `printf` or `microcom` can appear to hang while queued
output cannot drain.

The FF430 DTS now describes the CS3 device and reproduces the stock
timing/configuration value.  Modem release remains intentionally in the
appliance init script:

`devmem 0x53000000 8 0xff`

This command must run after the kernel configures the expansion bus and
before any process opens an Exar modem port.  Accessing the address
without the CS3 DTS configuration causes an IXP4xx imprecise external
abort.

## Remaining validation

Before treating the appliance kernel as final, test simultaneous traffic
on multiple modem channels, repeated open/close cycles, module reload or
a cold boot, and at least one sustained transfer.  Check that IRQ24 does
not climb continuously while all ports are idle and that the serial
overrun, parity, and framing counters remain stable during clean traffic.

The alternate interrupt and FIFO path is selected by the FF430-specific
reset-latch DT node, so unrelated boards using the broad XR17C15x setup
entry retain the generic 8250 behavior.  A future upstream submission
would still benefit from separating the board quirk from the generic
Exar PCI driver and replacing the userspace latch write with a dedicated
reset-controller or board driver.

## DS1302 real-time clock

The stock kernel contains a built-in DS1302 driver. Disassembly of that
kernel identified the RTC wiring without requiring board-level GPIO
probing:

-   GPIO2: SCLK
-   GPIO4: bidirectional I/O
-   GPIO5: active-high CE

The modern DTS represents the device using `spi-gpio`, `spi-3wire`,
`spi-lsb-first`, and `spi-cs-high`. Linux 5.15's `spi-gpio` advertises no
LSB-first support and its word helpers shift MSB first, so
`ff430-spi-gpio-lsb-first.patch` adds word reversal around the existing
bitbang helpers and advertises `SPI_LSB_FIRST`.

The first RTC access was initially sensitive to otherwise unrelated
kernel configuration changes. Oscilloscope captures showed the
unthrottled GPIO clock varying from roughly 1.2 to 2 MHz, but slowing it
did not fix the failure. Failed probes returned `0xff`; after an
unbind/bind cycle, the same kernel consistently worked. The relevant
datasheet requirement is CE inactive time, specified as 1--4 us
depending on supply voltage. At initial registration, the first probe
could follow CE initialization too closely.

`ff430-ds1302-ce-inactive-delay.patch` therefore leaves CE inactive for
10--12 ms before the probe's first transaction. This is deliberately
conservative, has negligible boot-time cost, and avoids depending on
incidental kernel layout or scheduling delays. The resulting driver has
survived repeated cold boots, sets the system clock during boot, and
continues to work across repeated `hwclock -r` and driver unbind/bind
cycles.
